# Hooks

Hooks let `gji` run your setup and cleanup commands automatically at key lifecycle moments.

If you only need to copy gitignored local files such as `.env.local` into new worktrees, use [`gji sync-files`](./configuration#sync-private-local-files) instead of a custom hook. Hooks are best for commands that actually need to run.

## Example

```json
{
  "hooks": {
    "afterCreate": ["pnpm", "install"],
    "afterEnter": ["printf", "switched to %s\n", "{{branch}}"],
    "beforeRemove": "pnpm run cleanup"
  }
}
```

This is the simplest way to make each new worktree feel “ready” instead of empty.

## Available hooks

| Hook | Event | Triggered by | Runs in |
| --- | --- | --- | --- |
| `afterBranchCreate` | A new branch was created. | `gji new` when it creates a branch, with or without `--branch-only` | The worktree that holds the new branch |
| `afterCreate` | A linked worktree was created and bootstrapped. | `gji new` (except `--branch-only`), `gji pr`, and `gji go` when it creates a worktree for an existing branch | The new worktree |
| `afterEnter` | An existing worktree was entered. | `gji go` and `gji back` | The entered worktree |
| `afterSwitch` | The current worktree switched to another branch in place. | `gji new --branch-only` | The current worktree |
| `beforeRemove` | A linked worktree is about to be removed. | `gji done` and `gji clean`, once per worktree it attempts to remove | The worktree being removed |

Put dependency installation and other worktree setup in `afterCreate`: it is
the only hook that runs after `gji` bootstraps a new worktree directory.
`afterBranchCreate` and `afterSwitch` also run for `--branch-only`, where no
new directory exists, so keep them limited to branch-level work such as
recording a ticket or printing a reminder.

When one command triggers several events, hooks run in this order:

- `gji new <branch>`: `afterCreate`, then `afterBranchCreate`.
- `gji new --branch-only <branch>`: `afterBranchCreate`, then `afterSwitch`.

`gji new` and `gji pr` do not run `afterEnter` after creating a worktree.
`afterBranchCreate` only runs for branches started from a base branch: `gji new`
skips it when it checks out a branch that already exists, and the local
branches that `gji pr` and `gji go` create from pull request or remote refs
only trigger `afterCreate`. `gji go --json` skips `afterEnter` so its output
stays machine-readable.

`beforeRemove` runs just before `gji` attempts the removal. If the removal then
fails, or you decline the prompt to force-remove a dirty worktree, the
worktree stays in place after the hook has already run.

In `--json` mode, hook stdout is discarded so the JSON output stays parseable.

## Template values

Hooks receive these template variables:

- `{{branch}}`
- `{{path}}`
- `{{repo}}`
- `{{slot}}` — stable worktree slot number.

The same values are also available as environment variables:

- `GJI_BRANCH`
- `GJI_PATH`
- `GJI_REPO`
- `GJI_SLOT` (for worktrees created by gji; the main worktree uses slot `0` once gji has created a linked worktree)

## Safer hook commands

Prefer argv-array hooks when you do not need shell features:

```json
{
  "hooks": {
    "afterCreate": ["pnpm", "install"],
    "afterEnter": ["printf", "switched to %s at %s\n", "{{branch}}", "{{path}}"]
  }
}
```

Array hooks run without a shell. Each array item is passed as exactly one argument, so branch names and paths containing spaces or shell metacharacters are not re-parsed as shell syntax.

String hooks are still supported for shell features like `&&`, pipes, redirects, shell functions, and `nvm use`. Template values are interpolated before the shell parses the command, so avoid putting `{{branch}}`, `{{path}}`, or `{{repo}}` directly into shell strings.

For shell-string hooks, read the context from environment variables and double-quote each expansion:

```json
{
  "hooks": {
    "afterCreate": "pnpm install && printf 'ready: %s\n' \"$GJI_PATH\""
  }
}
```

Avoid unquoted template values in shell strings, such as `echo {{branch}}` or `cd {{path}}`.

## Layering behavior

Hooks can come from:

1. global config
2. per-repo global overrides
3. local `.gji.json`

Different hook keys merge together. The same hook key is overridden by the highest-precedence layer.

That makes it possible to have a general default like `afterEnter`, while one repository overrides only `afterCreate`.

## Manual execution

You can rerun any hook from the table above in the current worktree:

```bash
gji trigger-hook <hook>   # for example: gji trigger-hook afterCreate
```

This is useful after cloning on a new machine or when you need to rebuild a worktree’s setup without recreating it.

## Practical examples

### Install dependencies for each new worktree

```json
{
  "hooks": {
    "afterCreate": ["pnpm", "install"]
  }
}
```

### Print context on entry

```json
{
  "hooks": {
    "afterEnter": ["printf", "switched to %s at %s\n", "{{branch}}", "{{path}}"]
  }
}
```
