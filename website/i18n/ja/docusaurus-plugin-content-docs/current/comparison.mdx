# gji は自分の作業に合いますか？

レビュー、機能開発、調査、実験など、ある Git の作業を開いたまま別の作業に取り組むことが多い場合に、gji は役立ちます。タスクごとに別のディレクトリを用意し、シェルから戻りやすくすることに重点を置いています。

## やりたい作業から選ぶ {/* #start-with-the-job-you-need-done */}

| やりたいこと | 選択肢 |
| --- | --- |
| タスクを開いたまま別のタスクに移動する | gji：ワークツリーを作成し、設定して移動し、元の作業に戻ります |
| Git で直接ワークツリーを管理する | [git worktree](https://git-scm.com/docs/git-worktree)：リンクされたワークツリーの作成、一覧表示、削除 |
| ターミナル UI で Git を操作する | [lazygit](https://github.com/jesseduffield/lazygit)：リポジトリの対話的な確認と操作 |
| リポジトリを複製してルートを探す | [ghq](https://github.com/x-motemen/ghq)：ディスク上のリポジトリを整理します |

これらのツールは組み合わせて使えます。たとえば、`ghq` でリポジトリを探し、gji でタスクに入り、そのワークツリーで `lazygit` を起動できます。この表は用途の違いを示すもので、ベンチマークや全機能の比較ではありません。

## Git ワークツリーに gji が加えるもの {/* #what-gji-adds-to-git-worktrees */}

別々の作業ツリーを提供するのは Git です。gji は、その周辺で繰り返す手順をつなぎます。

- `gji new` はブランチとディレクトリを作成し、対応する依存関係の設定を実行して、シェルを移動します。
- `gji pr 1234` は GitHub PR を別の作業ディレクトリに取得します。
- `gji go` は登録済みのリポジトリをまたいで、開いているタスクを探します。
- `gji back` は直前のワークツリーに戻ります。
- `gji done` と `gji clean` は状態を確認し、確認メッセージを表示して完了したワークツリーを削除します。

シェル連携を読み込むと、次のように割り込みに対応して元の作業へ戻れます。

```bash
# Your feature is already open in its own worktree.
gji pr 1234
# Inspect and test the PR here.
gji back
# Continue your feature with its changes still in place.
```

自分のリポジトリの実際の PR 番号を使ってください。新しいワークツリーでは依存関係のインストールが必要な場合があります。既存のワークツリーは、それぞれのインストール状態を保持します。

## 既存の環境で十分な場合 {/* #when-your-existing-setup-may-be-enough */}

一度に 1 つのブランチだけで作業し、別の作業コピーがほとんど不要なら、CLI を追加しても効果は小さいかもしれません。セットアップや移動を処理するディレクトリ構成とスクリプトがすでにあるなら、`git worktree` だけで十分な場合もあります。

## コストと制約 {/* #costs-and-boundaries */}

- ワークツリーごとにファイルと依存関係を置くディスク容量を使います。初回のセットアップには時間がかかります。
- ワークツリーはリポジトリの履歴と参照を共有します。サービス、ポート、外部データは分離しません。
- 現在のシェルを自動で移動するには、シェル連携が必要です。
- 移動時に未コミットの変更を移すことはありません。その操作は `new --take` で明示的に行います。
- 削除時には、ブランチや未コミットのファイルを削除する場合があります。取り消しで復元するのは記録済みの Git とワークツリーの状態であり、未コミットのファイルではありません。

これらの特性が合いそうなら、[クイックスタート](./quick-start)を試してください。最初の目標は、多くのコマンドを覚えることではなく、開いたままの作業に戻ることです。
