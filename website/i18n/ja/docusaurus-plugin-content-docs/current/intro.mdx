# タスクを切り替えても、作業はそのまま。

レビューを頼まれるたびに、開発途中の作業を片付ける必要はありません。`gji` はタスクごとに独立した作業ディレクトリを用意し、シェルから移動できるようにする Git ワークツリー CLI です。

## タスクごとに残るもの {/* #what-stays-with-each-task */}

作業ファイル、インストールした依存関係、生成ファイルは、そのタスクのディレクトリに置かれます。新しい機能、PR レビュー、実験のために別のワークツリーを開いても、元のワークツリーのファイルはそのまま残ります。

```bash
# While working on feature/payments:
gji new feature/search
gji pr 1234
gji go feature/payments
```

`1234` は、利用しているリポジトリの実際の GitHub PR 番号に置き換えてください。シェル連携を有効にしていれば、最後のコマンドで `feature/payments` に戻れます。残しておいた未コミットの変更もそのままです。

各ワークツリーでは、いつもの Git コマンド、エディタ、コーディングツールを使えます。`gji` が扱うのはワークツリーの作成、移動、セットアップ、削除です。コミットやレビューの手順を置き換えるものではありません。

## こんなときに役立ちます {/* #when-it-helps */}

- 機能開発に未コミットの変更があるまま、PR をレビューする必要があるとき。
- 使用中のチェックアウトを変えずに、アイデアを試したいとき。
- 複数のブランチで異なる依存関係や生成ファイルが必要なとき。
- 人が進めるタスクと AI を使うタスクを並行して開き、それぞれのファイルを分けたいとき。

Git ワークツリーはリポジトリの履歴と参照を共有します。コンテナではないため、サービス、ポート、外部データベースなどのマシン上のリソースは、プロジェクト側で分離または設定する必要があります。また、ワークツリーごとにファイルと依存関係を置くディスク容量を使います。

## 最初に確かめること {/* #your-first-success */}

[gji をインストール](./installation)してシェル連携を有効にしたら、[クイックスタート](./quick-start)を試してください。ワークツリーを作り、元のワークツリーに戻って、ファイルが残っていることを確認します。

その後は、目的に応じて次のドキュメントをご覧ください。

- [日常のワークフロー](./daily-workflow)：レビュー、実験、移動。
- [設定](./configuration)：既定のエディタとローカルのセットアップ用ファイル。
- [同期と削除](./sync-and-cleanup)：タスクを更新、または削除するとき。
- [比較](./comparison)：gji が自分の作業に合うか判断するとき。
