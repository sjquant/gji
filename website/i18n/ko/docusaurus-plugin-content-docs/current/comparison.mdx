# gji가 내 작업에 맞을까요?

리뷰, 기능 개발, 조사, 실험처럼 한 Git 작업을 열어 둔 채 다른 작업을 자주 한다면 gji를 선택하세요. 작업별로 디렉터리를 나누고, 셸에서 하던 작업으로 쉽게 돌아올 수 있게 하는 도구입니다.

## 하려는 일에 맞는 도구를 고르세요 {/* #start-with-the-job-you-need-done */}

| 필요한 일 | 시작하기 좋은 도구 |
| --- | --- |
| 작업을 열어 둔 채 다른 작업으로 이동 | gji: 워크트리 생성, 설정 실행, 진입, 돌아오기 |
| Git으로 워크트리 직접 관리 | [git worktree](https://git-scm.com/docs/git-worktree): 연결된 작업 트리 생성, 나열, 제거 |
| 터미널 UI에서 Git 작업 수행 | [lazygit](https://github.com/jesseduffield/lazygit): 대화형으로 저장소 검사와 조작 |
| 저장소 복제와 루트 위치 찾기 | [ghq](https://github.com/x-motemen/ghq): 디스크의 저장소 정리 |

이 도구들은 함께 사용할 수 있습니다. 예를 들어 `ghq`로 저장소를 찾고, gji로 작업에 들어간 뒤 그 워크트리 안에서 `lazygit`을 실행할 수 있습니다. 이 표는 각 도구의 초점을 비교하며, 성능 측정 결과나 모든 기능을 비교한 것은 아닙니다.

## Git 워크트리에 gji가 더하는 것 {/* #what-gji-adds-to-git-worktrees */}

별도의 작업 트리는 Git이 제공합니다. gji는 워크트리를 사용할 때 반복하는 과정을 이어 줍니다.

- `gji new`는 브랜치와 디렉터리를 만들고, 지원하는 의존성 설정을 실행한 뒤 셸을 이동시킵니다.
- `gji pr 1234`는 GitHub PR을 별도 작업 디렉터리로 가져옵니다.
- `gji go`는 등록된 여러 저장소에 걸쳐 열려 있는 작업을 찾습니다.
- `gji back`은 방금 떠나온 워크트리로 돌아갑니다.
- `gji done`과 `gji clean`은 상태 검사와 확인을 거쳐 끝난 워크트리를 제거합니다.

셸 통합을 불러오면 다음과 같이 작업을 전환했다가 돌아올 수 있습니다.

```bash
# Your feature is already open in its own worktree.
gji pr 1234
# Inspect and test the PR here.
gji back
# Continue your feature with its changes still in place.
```

저장소의 실제 PR 번호를 사용하세요. 새 워크트리는 의존성 설치가 필요할 수 있으며, 기존 워크트리는 자체 설치 상태를 유지합니다.

## 기존 도구만으로 충분한 경우 {/* #when-your-existing-setup-may-be-enough */}

한 번에 한 브랜치에서 작업하고 두 번째 작업 사본이 거의 필요 없다면 CLI를 추가해도 큰 도움이 되지 않을 수 있습니다. 설정과 이동을 잘 처리하는 경로 구조와 스크립트가 이미 있다면 `git worktree`만으로도 충분할 수 있습니다.

## 사용 전에 알아둘 비용과 제약 {/* #costs-and-boundaries */}

- 워크트리마다 파일과 의존성을 위한 디스크 공간이 필요합니다. 첫 설정에는 시간이 걸립니다.
- 워크트리는 저장소 이력과 참조를 공유합니다. 서비스, 포트, 외부 데이터를 격리하지 않습니다.
- 현재 셸을 자동으로 이동시키려면 셸 통합이 필요합니다.
- 이동할 때 gji는 미커밋 변경 사항을 옮기지 않습니다. 그 작업은 `new --take`로 명시적으로 수행합니다.
- 정리하면 브랜치와 미커밋 파일이 삭제될 수 있습니다. 실행 취소는 기록된 Git 및 워크트리 상태를 복원할 뿐, 미커밋 파일은 복구하지 않습니다.

이런 특성이 내 작업에 맞는다면 [빠른 시작](./quick-start)을 따라 해 보세요. 처음에는 명령을 많이 외우기보다, 열어 둔 작업으로 다시 돌아와 보세요.
